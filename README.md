# 军师 / GoutouJunshi

面向微信 iOS 8.0.75 的手动沟通分析插件。当前代码是第一版实现，**新版已通过 GitHub Actions/Theos 编译、链接、签名和 deb 打包；私有消息列表适配及新增功能仍待真机验收**。成功构建的代码提交为 `979bc43`：[Actions 构建 #12](https://github.com/fuyan8910-prog/goutou/actions/runs/36347778998)。

## 使用

1. 微信启动约 5 秒后出现可拖动的「军师」按钮。进入具体聊天后点击。
2. 在设置中输入 DeepSeek API Key；需要时修改模型名称（默认 `deepseek-chat`，以账户实际可用模型为准）和聊天条数（5～500，默认 20）。
3. 查看识别到的联系人、读取范围和「实际发送内容」。确认分析后才会联网。读取失败时不发起请求。
4. 展示关系状态、可能意图、局面、风险、策略及 3～5 条不同风格回复。点击回复只复制到本机剪贴板，5 分钟后过期；用户自行返回微信粘贴发送。
5. 长期记忆默认关闭。开启后可编辑关系、人物、事件、明确记住的信息和精简摘要。AI 摘要只在点击保存时写入；不会自动将推测变为关系事实。

## 扩展上下文与连续记忆

- 条数设置可选 5～500；不会自动加载微信数据库或拉取历史。需要更多时先向上翻页让微信加载，再打开插件；如果微信只保留 50 条在页面中，提高设置也不能凭空获得更多。分析页显示设置数量、可用数量、实际数量、文字量、起止时间。
- 不读取或显示联系人微信号、昵称、备注。使用微信账号和当前会话的内部标识隔离记忆，沿用原有文件键与路径，已有记忆无需迁移；内部标识不作为独立字段发送给 AI。界面称呼为“当前聊天对象”或“当前群聊”。
- 记忆采用多行编辑页及长度计数。AI 生成累计摘要时结合旧摘要与本次聊天，提示保留重要背景、时间、边界、承诺、未解决话题和表达习惯；冲突及推测明确标注。候选回复不算已发送。
- 累计摘要目标不超过 3000 中文字符，程序拒绝超过 4000 UTF-16 单元的摘要，避免静默截断保存。只在手动保存时替换累计摘要；前四项手动记忆不会被 AI 修改。核对摘要后再保存，尤其重要的事实应记入前四项。AI 合并仍可能遗漏，不能保证无限历史或每次绝对连贯。
- 请求输出预算提高至 8000 tokens，为累计摘要留出空间。文字上限不是 token 计数，实际模型上下文限制仍可能拒绝请求；可减少聊天条数或精简记忆。

## 省量回复与升级兼容

- 每次打开默认“日常回复”：只读最近20条已加载消息，历史记忆仅作背景；完整携带累计摘要和明确记住的信息，关系/人物/事件分别最多600/600/800 UTF-16单元。截短只影响本次请求，不修改本地原文，实际内容可预览。
- 日常模式输出预算1800 tokens，提示返回简短分析、回复目标和3条候选，不生成或保存摘要；预算上限不是每次实际消耗。
- “最近对话更新记忆”发送旧记忆和最近20条，手动核对并保存合并摘要。它不是带持久游标的全量增量同步：两次更新之间超过20条或页面未加载的消息可能不被覆盖，需要时用深入分析补充。
- “深入分析”沿用设置中的5～500条，历史单独放入historical_background，最新20条放入current_conversation；所有模式候选回复只围绕当前话题。可手动指定回复话题，结果显示reply_target；最新一条是自己发送时不假装对方又发了消息。
- 同一面板内，相同账号、会话、模式、模型、记忆版本和请求内容可复用上次成功结果，不再调用API。“重新生成”需要再次确认并使用API；关闭面板后不保留这份临时缓存。
- 继续使用“军师”名称。包标识、Keychain服务名、偏好域、记忆目录及账号/联系人文件键全部不变。新版可读取旧版手动保存的五项记忆，不需要重复分析500条；只分析但没保存的结果无法恢复。
- 覆盖更新须保留同一微信沙盒/数据容器。卸载微信或改变签名导致新数据容器时不能保证数据沿用；注入时替换旧插件，勿同时载入两个版本。

## 个人语气匹配

- 在当前联系人记忆中新增“我的语气与回复样例”，最多4000 UTF-16单元，建议填3～5句自己真实说过的话及简单偏好。启用长期记忆后发送；关闭记忆不读取、不发送；留空保存或清除联系人记忆可删除。AI摘要保存不会覆盖它。
- 所有模式最多抽取当前已读取范围内最近12条自己发出的文本，每条最多160 UTF-16单元，明确作为风格样本；不把对方消息当作用户风格，不额外读取历史或额外调用API。样本与正文会有少量重复输入。
- 候选在回应思路上有区别，但保持相同用户口吻；约束句长、用词、称呼、标点、表情和亲密程度。旧样例不作为当前话题。缺少样本时提示不足，以简短中性表达代替杜撰风格。
- 更新累计摘要时提示保留“我的表达习惯”小段，仍需用户确认保存。日常回复不自动写记忆；旧摘要未保存风格时无法凭空恢复，补充手动样例即可，无需重新分析500条。
- 原五项记忆与文件键继续兼容，第六项缺失时按空字符串处理。全部六项填满最多约24000 UTF-16单元。口吻匹配是生成约束，效果仍需真机和实际回复确认。

## 微信适配边界

- 不 hook 假定存在的旧版聊天控制器，不声明或链接 `CMessageWrap`。AI/UI/Memory 仅使用统一模型。
- 从当前可见控制器及有限层级父控制器，尝试 `getChatUsername` 或联系人字段。通过动态 `MMServiceCenter/defaultCenter/getService:` 获取 `CContactMgr`，尝试 `getSelfContact`、`getContact:`。这些类、方法、字段仍需真机确认。
- 对私有方法检查 `respondsToSelector:`、参数个数、对象/类参数与对象返回 ABI；用 `NSInvocation` 调用。对象字段检查 ivar 类型，数值字段使用有异常保护的限定 KVC。找不到内容则显示错误。异常保护不能保证任意微信内部方法自身永不发生底层崩溃。
- 首先检查候选消息数组字段，再有界枚举当前控制器名称包含 `msg/message` 的对象 ivar；最多 16 个候选，每个只检查末尾最多 2000 个节点（联系人交叉校验另检查末尾 200 个节点）。仅接受数组，展开 `m_msgWrap` 后校验当前账号/会话归属、类型和时间。候选字段不是已经证实的 8.0.75 接口。
- 按时间稳定排序，取设置条数，单条上限 2000 UTF-16 单元（超长显示截断标记），总文本上限 60000；不切断 Unicode 组合字符。相同秒消息保留读取数组中的顺序，不宣称绝对原始顺序。
- **只读取页面已加载记录，可能是向上翻页后的旧记录，不能保证数据库最新 N 条。** 界面明确提示这一限制；不会伪造历史，不调用来源未知的 `getMessageFrom:maxCount:`，也不扫描数据库。
- 群聊仅在会话归属字段符合校验时处理，尝试 `m_nsRealChatUsr` 区分参与者；参与者缺失时无法可靠区分发言人，必须核对预览，群聊行为待真机验收。
- 图片、语音、视频、表情、分享等只转换为占位文字，不上传媒体、附件、XML 或整个数据库。
- 本机适配诊断只显示控制器类、候选字段名及服务类存在性，不打印数据、Key 或网络日志，不上传诊断。

## 隐私与安全存储

- 无自动发送、自动回复或消息发送接口调用。网络入口只在用户确认分析后执行。
- Key 使用 `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`，仅在钥匙串保存；失败提示系统错误码，不回退到明文。是否可访问钥匙串取决于注入/重签名环境的 entitlement，须真机确认。
- 记忆文件位于微信沙盒 `Library/Application Support/GoutouJunshi/Memory`。文件名由账号和联系人二元组的 SHA-256 得出，防路径注入、跨联系人和跨账号串用。哈希文件名不是内容加密；内容由 iOS `NSFileProtectionComplete` 保护，并将目录排除系统备份。同一宿主进程的其他代码不在隔离边界内。
- 每个记忆字段最多 4000 UTF-16 单元，五项共最多 20000；旧记忆原路径兼容，无需清除。关闭记忆后不读取、上传、写入；已有文件保留至用户清除。清除联系人、全部清除、开关变化及手动编辑都会使旧分析的写回资格失效。
- 发往固定 `https://api.deepseek.com/chat/completions` 的内容为受限上下文与启用时的精简记忆。用户 ID 不作为单独字段发出，发言者改用单聊「我/对方」、群聊「我/群成员 N」（群成员编号不跨请求稳定）；**原聊天正文、用户记忆可能仍含姓名、号码等个人信息，预览并不等于自动脱敏**。
- 使用 ephemeral URLSession，不缓存、不持久化 Cookie、拒绝重定向、响应最多 256 KiB、请求/资源超时 180/240 秒，无自动重试。取消无法撤回服务端已收到的数据。
- JSON 输出按 [DeepSeek 官方 JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode/)构造；客户端仍验证结果类型、必要字段、回复数量与长度，并拒绝截断响应。

## 构建与检查

`Makefile` 明确列出 10 个 `.m/.xm` 编译单元，保持 `arm64`、`iphone:clang:latest:15.0`、ARC 和安装进程；增加 Security、QuartzCore，保留 UIKit、Foundation。`control`、`GoutouJunshi.plist`、`.github/workflows/build.yml` 未改动。

现有 Actions 继续在 macOS 安装 Theos 后执行 `make clean`、`make package FINALPACKAGE=1` 并上传 `packages/*.deb`。完整工程已上传 main 并完成远程构建，产物为 `com.fuyan.goutoujunshi_0.1.0_iphoneos-arm64.deb`。Windows 当前环境无 Theos/Clang/iOS SDK，实际编译验证由现有 Actions 完成。首轮发现并修复了 Objective-C 子控制器属性名，应使用 `childViewControllers`。

可运行 `python scripts/check_source.py` 检查源文件列表、依赖和禁止的跨模块访问。安装 `tree-sitter`、`tree-sitter-objc` 后还会解析 Objective-C 语法；`%ctor` 仅在内存中替换为普通构造函数以检查主体。**语法解析不等于 Clang/Logos 编译，不验证 SDK、ABI 或真实微信行为。**

本次已执行静态边界检查、所有 20 个源码/头文件的语法解析和 `git diff --check`。人工复核 ARC/CF 桥接、网络 delegate 生命周期、取消旧回调、私有调用类型、nil 路径及 iOS 15 公共 API 使用；没有禁用 `-Werror` 或 deprecated 警告。
